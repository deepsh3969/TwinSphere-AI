# TwinSphere AI — Operations Guide

Runbook for operating a deployed TwinSphere instance.

---

## Health & readiness

| Endpoint | Auth | Purpose |
|----------|------|---------|
| `GET /health` | none | Liveness: backend, database, simulation engine, AI engine, version |
| `GET /api/system/status` | `read` | Readiness-style detail: AI status, metrics, clock, speed, scenarios |
| `GET /api/system/metrics` | `read` | Bounded operational counters (HTTP, WS, sim lifecycle, rate limits) |

`/health` returns `status: "degraded"` when the database is unreachable —
use it as the container/process healthcheck.  It never exposes secrets or
detailed internal configuration.

**Liveness vs readiness:** `/health` is liveness (is the process up?).  A
deeper readiness probe can poll `/api/system/status` with a valid token and
check `health.database == true`.

## Structured logs

Format: `%(asctime)s %(levelname)s %(name)s: %(message)s`

Key loggers:

| Logger | What it emits |
|--------|--------------|
| `twinsphere` | Startup, lifespan, unhandled errors |
| `twinsphere.ws` | WebSocket connect/disconnect/broadcast failures |
| `twinsphere.runtime` | Sensor tick, sim tick, AI refresh |
| `twinsphere.demo` | Demo run lifecycle |

Every HTTP response includes `X-Request-ID` (client-supplied or generated).
Unhandled exceptions log the full traceback server-side and return a generic
`{"detail": "Internal server error"}` to the client — never leak exception
classes or stack traces.

---

## Correlation IDs

- Client can send `X-Request-ID: <value>` (8–64 chars `[A-Za-z0-9_-]`).
- The backend echoes it back on every response.
- Use it to correlate a user-reported issue with server logs.

## Database connectivity

- `/health` reports `database: "ok" | "unavailable"`.
- Connection failures surface as `500` with a generic message; the traceback
  is in the server log.
- SQLite: single file; back up by copying the file (see below).
- PostgreSQL: use `pg_dump` on a schedule.

---

## WebSocket diagnostics

- `GET /api/realtime/status` — connected clients, channel counts (requires auth).
- `GET /api/system/metrics` — `ws.connections.active` gauge, `ws.connections.total`
  and `ws.disconnects.total` counters.
- Auth failures close with code `4401`; rate-limit rejections with `4429`.
- Oversized messages close with `1009`.

---

## Simulation lifecycle failures

- Invalid transitions (start a RUNNING sim, pause a COMPLETED sim) return
  `400` with a descriptive message.
- Concurrent creates return `409` (single active simulation; TOCTOU-guarded
  by `_SIM_LOCK`).
- `POST /api/demo/reset` clears in-memory sim/route/anomaly state without
  deleting persisted history or audit rows.
- `POST /api/demo/hard-reset` re-initialises the entire twin state (admin
  only) and re-syncs the runtime loop's state reference.

## Resource monitoring recommendations

| Metric | Where | Alert threshold (starting point) |
|--------|-------|----------------------------------|
| `http.*.500` counter rate | `/api/system/metrics` | > 5/min |
| `ws.connections.active` | `/api/system/metrics` | > 100 |
| `ratelimit.*.blocked` rate | `/api/system/metrics` | sustained > 10/min |
| Process RSS | OS / cAdvisor | > 512 MB |
| Disk (SQLite volume) | OS | > 80 % full |
| DB size | `ls -lh twinsphere.db` | grows unbounded → archive |

The in-memory rate-limit buckets and metrics counters are per-process and
key-capped (10 000 / 400 respectively) — memory cannot grow without bound
from these structures.

## Backup & restore

### SQLite

```bash
# backup (safe while running — SQLite supports online backup via .backup)
docker compose exec backend python -c "
import sqlite3; src=sqlite3.connect('/data/twinsphere.db');
dst=sqlite3.connect('/data/backup.db'); src.backup(dst); dst.close()"
docker compose cp backend:/data/backup.db ./twinsphere-$(date +%F).db

# restore
docker compose down
docker compose cp ./twinsphere-2026-01-01.db backend:/data/twinsphere.db
docker compose up -d
```

### PostgreSQL

```bash
# backup
docker compose --profile postgres exec postgres \
  pg_dump -U twin twinsphere > twinsphere-$(date +%F).sql

# restore
docker compose --profile postgres exec -T postgres \
  psql -U twin twinsphere < twinsphere-2026-01-01.sql
```

### What is safe to lose vs not

| Data | Critical? | Notes |
|------|-----------|-------|
| Users / roles | **Yes** | Re-bootstrap with `bootstrap_admin` if lost |
| Audit logs | **Yes** (compliance) | Never truncated by demo reset |
| Simulation history | No (demo) | Regenerated by running new sims |
| Sensor readings | No (simulated) | Regenerated by the seed/runtime |
| Route events | No | Regenerated by route calculations |

Demo reset (`POST /api/demo/reset`) clears **only** in-memory state — it
never deletes users, audit rows, or persisted simulation/route history.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---------|-------------|-----|
| Backend exits at startup: "Refusing to start in production" | Dev `JWT_SECRET` or short secret with `APP_ENV=production` | Set a ≥ 32-char random `JWT_SECRET` |
| 401 on every request | Token expired or revoked | Re-login; check `JWT_EXPIRE_MINUTES` |
| 429 on login | Rate limiter (login 20/min per identity) | Wait 60 s, or set `RATE_LIMIT_ENABLED=false` for demos |
| WebSocket closes immediately | Auth timeout or invalid token | Send `{"type":"auth","token":"<jwt>"}` within `WS_AUTH_TIMEOUT_S` |
| Frontend shows "BACKEND OFFLINE" | Backend not running or CORS mismatch | Check `/health`; check `CORS_ORIGINS` |
| Empty analytics charts | No data in the selected window | Widen the range or run a simulation |
| Demo run returns 409 | Another demo run is active | `POST /api/demo/stop` first |
| `degraded` on `/health` | Database unreachable | Check `DATABASE_URL`, volume mounts, Postgres container |

## Security operations

- Rate-limit buckets are in-memory and per-process.  For multi-worker
  deployments, replace with a shared store (Redis) — see `docs/SECURITY.md`.
- `GET /api/audit` (admin) supports action/outcome/actor/date filters and
  request-id correlation.
- Disabled users are dropped from live WebSocket connections within 60 s
  (revalidation interval).
- Token revocation: `POST /api/auth/logout` (single) or
  `POST /api/auth/logout-all` (all sessions for the user).
